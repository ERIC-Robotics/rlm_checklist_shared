RLM Checklist Project – Operations and Database Guide

Purpose: This document explains what the project is, how it is deployed, where data is stored, how a trial is saved, and how to verify or troubleshoot saved data.

Last updated: 31 October 2026

1. Project overview

The RLM Checklist project is a Next.js web application used to sign in employees, create and edit railway/trial checklist forms, save trial information, submit agenda and pre-trial data, and manage support tickets.

2. Important database clarification

This application does not use Cloudflare D1 for trials. Cloudflare hosts the Worker, but employee records, trials, and support tickets are stored in Neon PostgreSQL through the DATABASE_URL environment variable.

Therefore, the Cloudflare D1 dashboard may show zero writes even when the application is saving correctly. To inspect trial data, use the Neon console and the trials table.

4. Database tables

In Neon, open the production branch, then go to Postgres database → Tables → neondb → public.

TablePurpose

5. How a trial is saved

  1. An employee signs in with an active employee code.
  2. The user creates a trial or opens an existing trial.
  3. When a form value changes, the browser immediately saves a local copy.
  4. After approximately 500 milliseconds, the browser sends a PUT request to /api/trials/[trialId].
  5. The API validates the session and writes the trial to Neon using an INSERT ... ON CONFLICT DO UPDATE query.
  6. The record is stored in the trials table. Form answers are stored in state as JSON.
Successful save check: The updated_at value in Neon changes to the latest save time. The date displayed in the trial title is form data and is not the database save timestamp.

6. How to verify a deployed save

  1. Open the deployed Cloudflare Worker URL.
  2. Sign in with an active employee code.
  3. Create a trial or change a field in an existing trial.
  4. Wait one or two seconds for autosave.
  5. Open Neon and select the correct production branch.
  6. Go to Postgres database → Tables → neondb → public → trials.
  7. Refresh the table, or run the SQL query below.
SELECT trial_id, title, owner_code, created_at, updated_at
FROM trials
ORDER BY updated_at DESC
LIMIT 20;

The newest row should have a current updated_at timestamp and the employee's owner_code. Neon timestamps are normally displayed in UTC; convert to local time when comparing with the computer clock.

7. Who can see a trial?

The trial list is intentionally filtered for security. A user can normally see a trial when its owner_code matches their employee code. Submitted, agenda-submitted, and pre-trial-submitted records are also visible according to the application rules. PMO users have additional access.

If a trial exists in Neon but is not visible in the deployed application, first compare the trial's owner_code with the employee code used to log in.

8. Required deployment configuration

Cloudflare Worker secrets are separate from local .env.local. The following values must be configured in the deployed Worker:

VariablePurpose
DATABASE_URLNeon pooled PostgreSQL connection string. It must point to the intended production project/branch.
AUTH_SECRETAt least 32 characters; signs employee session cookies.
AADHAAR_ENCRYPTION_KEYStable encryption key for external member Aadhaar values.
APP_BASE_URLPublic application URL used in approval links.
Email variablesCloudflare Email binding and/or SMTP settings for notifications.

After changing Worker secrets or source code, redeploy the application. Local changes and local .env.local values do not automatically update the live Worker.

9. Deployment commands

Run these commands from the application folder containing package.json:

npm ci
npm run build
npm run preview:cloudflare
npm run deploy:cloudflare

The production deployment command builds the OpenNext Worker and deploys it to Cloudflare.

10. Troubleshooting

SymptomLikely causeAction
D1 shows “Rows written: 0”D1 is not used by this application.Check Neon PostgreSQL instead.
Form looks saved on the same browser but no Neon row existsOnly the local browser cache saved, or the API save failed.Look for “Shared save failed” in the application and inspect Worker logs.
Trial exists in Neon but is not listedLogged-in employee does not have access to that owner_code, or the Worker points to another database.Compare employee code and confirm DATABASE_URL.
Login failsMissing database connection, employee is inactive, or AUTH_SECRET is missing.Check Worker secrets and the employees table.
Old data appears after deploymentWorker secret points to a different Neon branch/project.Compare the deployed DATABASE_URL with the production Neon connection string.

12. Security notes

  • Never put production secrets in wrangler.jsonc, source files, screenshots, or Git.
  • Keep DATABASE_URL, AUTH_SECRET, and AADHAAR_ENCRYPTION_KEY private.
  • Use the production Neon branch for the live Worker and verify the connection before deployment.
  • Do not treat the browser local cache as the shared source of truth.
